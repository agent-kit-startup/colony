# Mission Kit Colony

Colony is the Mission Kit desktop IDE: a Tauri 2 cockpit with Mission Control as its home screen. It drives the open [Agent Kit](https://github.com/agent-kit-startup/agent-kit) CLI and each vendor's own agent on the user's own subscription or API key.

Open source under the [Apache License 2.0](LICENSE) ([NOTICE](NOTICE)). Contributions come in under the Developer Certificate of Origin (`git commit -s`, see [CONTRIBUTING.md](CONTRIBUTING.md)). Colony collects no telemetry: its only network calls of its own are the engine and Node runtime downloads you start from `More → Engine…` (see [PRIVACY.md](PRIVACY.md)).

## Status

Cockpit alpha. Linux (Omarchy / Hyprland) is the first target.

The cockpit is the center of the window. Its first tabs are Mission Control itself, as native views fed by the kit's own data (see Mission Control data): Mission, Plans, Queue, Inbox, Review, Git, CI/CD and Flight Log (Ctrl+1 to Ctrl+8). Every agent run opens as its own tab next to them, and so does an interactive agent. Files open in tabs after those.

| Area | What works |
|------|------------|
| Workspace | `Open folder` (Ctrl+O), the folder as the first CLI argument, recent folders on the welcome screen. File access is limited to the opened folder. |
| Mission | Home tab: the active plan from HANDOFF (lifecycle, progress, current and next to-do, gaps), `▶ Run plan`, `⏭ Run queue`, `⌘ Open interactive`, the engine picker, then cards for what needs you (live gates answerable in place, attention items, gate-exit tickets), the agent runs, the saved chats (see Chats), the queue, the flight log, recent activity and the repository (branch flow, health checks). **Agent runs** lists every run Colony launched in this window: driver runs (the queue runner included, shown with its queue position and current plan), interactive vendor CLI tabs (plan actions such as `Run…` included) and queue runner terminal tabs, with plan, engine, state (starting, running, awaiting gate, ended with its exit code), start time and elapsed time; a click focuses its tab. Runs the kit snapshot reports (`run_plan` activity, agent processes of the folder) are merged in, without duplicating a Colony launch. A run Colony launched on a plan HANDOFF does not name yet (e.g. `/run-plan <plan>` in an interactive tab) shows as the active run, marked "launched from Colony", until HANDOFF switches to it; `▶ Run plan` still runs the HANDOFF plan. The queue card shows the queue as held when HANDOFF names another plan than the queue cursor while `Queue status` says running, or when a live queue run reports `held`. While a queue driver run is live, the hero shows its position, current plan, status and open gate; a click opens its tab. |
| Plans | Every plan of the snapshot with filters (open, in queue, backlog, parked, incomplete, completed, all) and search, progress, queue role; a row expands to its to-do list. Actions: `Open` (editor), `▶ Run` on the HANDOFF plan (driver run), `Run…` on any other open plan, `Edit…` on a backlog plan and `Resume…` on a parked, incomplete or executing one: those open your agent interactively with `/run-plan <plan>`, `/backlog-edit <plan>` or `/continue-plan <plan>` after a confirmation (`agent-kit run-plan` has no plan argument; it always runs the HANDOFF plan). |
| Queue | The `run-plan-all` queue from HANDOFF: order, cursor, outcomes, each plan's lifecycle and progress, the queue status note. `⏭ Run queue` starts the queue runner after a confirmation. On an engine with driver protocol 1.2.0 or newer (read from `engine.json`, or `engine-info --json` for `COLONY_AGENT_KIT_BIN` and the PATH fallback) it is a driver run, `agent-kit run-plan-all --events ndjson --backend <engine>`, in its own agent tab: its gates appear in the Inbox and are answered there, and the cursor and status follow its `queue_state` events (read-only, Colony never moves the cursor). On an older or unknown engine it opens in a terminal tab, where its numbered-list gates are answered. |
| Agent tab | One center tab per `agent-kit run-plan --events ndjson` run, opened and focused when the run starts (from `▶ Run plan`, a view, or `More → Run plan in another folder…`). A readable transcript: assistant text as prose, tool calls collapsible with their results, thinking folded, each tick's `LOOP_TICK_RESULT` as a summary card (exit, pending before and after, stop, usage limit, link to its Review), HITL gates inline with answer buttons and free text, answered gates marked. `Raw log`, `Stop at gate`, `Kill`. A collapsible **Context sources** strip under the head lists what that agent loads for its folder (see Open interactive). Several runs at once, one per folder (the kit has no run lock). Needs a folder with the kit installed and an active plan. |
| Open interactive | `⌘ Interactive` opens the engine's own CLI, unmodified (`claude` or `codex`; the Cursor engines open whichever of those is on PATH), in a center terminal tab in the opened folder, with the picker's model. Colony passes no credentials and reads none: the CLI uses your own login, and its environment is the same as a shell tab's. Agent tabs (driver runs, interactive and queue runner terminals) show a collapsible **Context sources** strip: what the agent loads for that folder, each with existence, line count and size, a click opens it in your editor. Claude: `~/.claude/CLAUDE.md`, `CLAUDE.md` (and `CLAUDE.local.md`) of the folder and of each parent up to your home folder, `AGENTS.md`, `.cursor/HANDOFF.md` and the auto-memory `~/.claude/projects/<folder with every non-alphanumeric character as ->/memory/MEMORY.md` with the count of memory files next to it (Claude Code keys that memory by the start folder, so a session started elsewhere loads another project's memory). Codex: `~/.codex/AGENTS.md`, `AGENTS.md` from the repository root down to the folder, HANDOFF. Cursor engines: `AGENTS.md`, `CLAUDE.md`, `.cursor/rules`, HANDOFF. Only paths, sizes and line counts are read (`src-tauri/src/context.rs`); a listed file outside the folder may then be opened like the settings file. |
| Chats | The Mission view's **Chats** card lists the agent sessions saved for the opened folder, newest first: title, when it was last saved and the short session id. Claude Code saves every session per start folder (`~/.claude/projects/<folder with every non-alphanumeric character as ->/<session id>.jsonl`), so the list shows the sessions started in this workspace folder; subagent transcripts are not listed. The title is the name you gave the session, else Claude Code's own title, else the first prompt. A click (or `Resume`) opens `claude --resume <session id>` in a terminal tab in the folder, labelled with the title (the id is checked as a UUID before it reaches the command line; the session keeps its own model); a chat already open in a resume tab is focused instead. `↻ Refresh` reads the list again; it is also read when a folder opens and when an interactive claude tab ends. Up to 200 sessions are listed, with the total. Only the titles are read, line by line, and cached by file size and time (`src-tauri/src/chats.rs`). Codex and Cursor sessions are not listed yet. Terminal tabs themselves are not restored after a restart. |
| Inbox | Live gates: every open HITL gate from every run in this window, any engine, oldest first (tab badge = their count). A button or free text answers it: the driver-protocol line `{"type":"hitl_reply","askId":...,"reply":...}` goes to that run's stdin only. A card leaves when it is answered, the tick ends or the run exits. Colony never answers a gate by itself. Below: Mission Control's attention items (open the file, or `Ask agent` for an allowlisted kit command such as `/plan-review-triage`; anything else copies) and pending gate-exit tickets. |
| Review | Every tick of every run in this window with the files it changed (added, modified, deleted, renamed; new untracked files included, `.gitignore` respected), a Monaco side-by-side diff per file, commits made during the tick, the `LOOP_TICK_RESULT` line, "Copy patch". A tick is the working tree change from the previous tick end (or the run start) to its own end, captured as git tree objects through a throwaway index, so your index, worktree and refs are never touched; an edit you make between two ticks shows up in the next tick. A run killed mid-tick still gets its partial tick. |
| Git | Branch flow from the snapshot (upstream, vs staging, vs main, staging vs main), last commit and graph; working tree status, per-file diff, commit (optionally `git add -A`; hooks always run), push without force. Pushing a production branch needs a typed `yes`: `production`, `prod` and `release` always, and `main` / `master` only when the repository also has `origin/staging` (without `staging`, `main` is the development branch and pushes or merges into it are a plain click). Production promotion: Colony never runs `/git-prod` or any prod promotion; after a typed `yes` it copies `/git-prod` for your own agent session. Above them: **Requests**, one approval card per host request (see Host requests) with the request nonce, kind, arguments, reason, folder and the PR context (title, base ← head, mergeable state, checks, `View diff`, `Open PR`); the tab badge counts them. **Pull requests**: the open PRs with their checks summary and a `Merge…` button that opens the same card under the same production rule. |
| CI/CD | Recent workflow runs (`gh run list`) of the current branch, of the open pull request branches, or all, with `Rerun failed` (`gh run rerun <id> --failed`) on a failed run. |
| Flight Log | The current residual and earlier ones, operator warnings, gate-exit tickets, open triages, the ticks of this window's runs, and the headless tick logs (`.cursor/loop-logs`) with their result, sentinel and gates (open a log in the editor). "Copy fix prompt" copies. |
| Explorer | Lazy file tree (`.git` hidden), refresh button. |
| Editor | Monaco with one tab per file, dirty marker, Ctrl+S save, Ctrl+W close (asks before dropping unsaved changes), Ctrl+P quick open. |
| Terminals | Real PTYs running your `$SHELL` in the opened folder at the bottom, several tabs (`+` or Ctrl+Shift+T), Ctrl+` to show / hide, Ctrl+Shift+C / Ctrl+Shift+V copy and paste (wired, not yet verified on WebKitGTK). |
| Open in my editor | `Open in editor` (Ctrl+Shift+E) hands the active file, or the folder, to your own editor; right-click a file or folder in the Explorer for that one. |
| Engine picker | In the Mission tab: engine (`--backend`: `claude`, `codex`, `cursor-acp`, `cursor-agent`, `auto`; the ones not on PATH are marked), `--on-limit` engine for the next fresh tick after a vendor usage limit, optional `--model`, tick budget. Each choice is remembered for the opened folder in the settings file. The note under the picker says how a gate answer reaches that engine (`cursor-agent` has no input channel: a gate ends the tick). The same engine picks the vendor CLI for `Open interactive` and the backend of `Run queue`. |
| Web panel | `More → Mission Control (web panel)`: the kit's own page in a tab, as a fallback (see Mission Control web panel). |
| Skins | `More → Skin`: Bare Metal (default) or Legacy for the whole window, web panel included; saved as `ui.skin` in the settings file. |

Not yet: engine choice per to-do (the CLI picks the backend per run), a driver run of a plan other than the HANDOFF one (needs the kit: `run-plan` has no plan argument), per-tick reviews of a queue run (the queue runner is one session without ticks), backlog actions without an agent (the kit exposes them only as slash commands), OS keychain for vendor keys (left out: the product plan says the IDE never reads, stores or relays vendor tokens; the agent CLIs keep their own login), the Tauri updater, macOS and Windows builds.

## Install (Linux x86_64)

```bash
curl -fsSL https://colony.missionkit.io/install.sh | sh
```

`packaging/install.sh` checks the release signature (minisign key `9A9BB4349C2248C6`, with `minisign` or OpenSSL 3) and the sha256 before it installs anything, installs per user without sudo, and `--uninstall` removes it again. Releases come from a pushed `v<version>` tag (`.github/workflows/release.yml`). The download host is not live yet: see [docs/release.md](docs/release.md) for the release files, publishing, the identity checklist and the install smoke.

## Requirements (Linux)

- Rust stable via rustup (`~/.cargo/bin` on PATH for builds).
- Node.js 20+ and pnpm 10.
- Tauri 2 system libraries: `webkit2gtk-4.1`, `gtk3`, `libsoup3`, `base-devel` (Arch package names).
- An Agent Kit engine: `More → Engine… → Install engine` (see Engine), or `COLONY_ENGINE=<kit checkout>` for development. An `agent-kit` on PATH (`npm i -g @dadado/agent-kit-cli`) still works as a fallback, flagged as an unmanaged engine.

## Build and run

```bash
pnpm install --frozen-lockfile
pnpm tauri dev                   # development, hot reload on http://localhost:1420
pnpm tauri build                 # release binary + .deb bundle
./src-tauri/target/release/colony ~/code/some-repo
```

`pnpm tauri build` writes `src-tauri/target/release/colony` and `src-tauri/target/release/bundle/deb/Colony_<version>_amd64.deb`. A plain `cargo build --release` is not enough for a runnable binary: the Tauri CLI enables the custom protocol that serves the built frontend.

## Launcher (per user, no sudo)

```bash
pnpm tauri build
packaging/install-local-launcher.sh
```

This writes `~/.local/bin/colony` (wrapper around `src-tauri/target/release/colony`) and `~/.local/share/applications/colony.desktop`, so Colony shows up in the app launcher. `colony ~/code/some-repo` opens a folder directly. Rebuilding updates the same binary; the launcher does not need to be reinstalled.

## Settings

`~/.config/io.missionkit.colony/settings.json` (the ⚙ button creates it and opens it in a Colony tab). Read on every use: a saved edit applies at once.

```json
{
  "ui": { "skin": "bare-metal" },
  "editor": { "command": ["zed", "{path}"], "terminal": false },
  "workspaces": { "/home/me/code/repo": { "backend": "claude" } }
}
```

`ui.skin` is the look of the whole window: `bare-metal` (the default, neutral greys) or `legacy` (the slate palette of the kit's original Mission Control); `More → Skin` switches and saves it. Both are one design token set, `src/tokens.css`: a copy of the web Mission Control's own tokens under the same names (`--bg-primary`, `--border`, `--text-muted`, `--green-bg`, `--mc-radius-chrome`, `--mc-space-lg`, ...; source file and kit commit in its header), so a skin is the same nine surface colors in both. The chrome, the native views, Monaco and the terminals read it, and the web panel follows (see Mission Control web panel). The native views also reuse the web page's components: card headers with an icon and a title-case label, status pills, per-to-do segmented progress, the previous / current / next steps, monospace metadata rows and action chips (`src/ui.ts`, icons in `src/icons.ts`).

Open in my editor picks, in order: `editor.command` (a string split on spaces, or an argv array; the path is appended or replaces `{path}`), `$VISUAL`, `$EDITOR`, then `xdg-open`. `$VISUAL` / `$EDITOR` run in a new Colony terminal tab through `sh -c '<editor> "$@"'`, the way git runs them, so terminal editors (and wrappers such as `omarchy-launch-editor --inline`) work; a configured command runs detached unless it is a terminal editor (`nvim`, `vim`, `hx`, ...). `editor.terminal` forces either way. The path is always its own argument.

## Engine

Colony runs the open Agent Kit as a managed engine (the kit's ADR `2026-10-19_colony-managed-engine-distribution`): it installs, updates and rolls back the kit itself, and never needs npm. `src-tauri/src/engine.rs` resolves it in this order:

1. `COLONY_ENGINE=<path>`: a kit checkout or an extracted engine, for developing the engine and Colony against the same working tree. A checkout without `engine.json` is asked with `agent-kit engine-info --json`.
2. The managed engine in `<data dir>/colony/engine/<version>/` (Linux: `~/.local/share/colony/engine/`): the current one of `state.json`, else the highest installed version Colony supports.
3. `agent-kit` on PATH, as before; the status bar says `⚠ unmanaged engine`.

`COLONY_AGENT_KIT_BIN` and `COLONY_DASHBOARD_SERVE` still win for agent runs and for Mission Control (the smoke fixtures use them).

Supported range: driver events protocol 1.x and Mission Control data 1.x (`DRIVER_PROTOCOL_MAJOR`, `DASHBOARD_DATA_MAJOR` in engine.rs), read from the engine's `engine.json`. A kit release inside the range installs without a Colony release; a new major is refused until Colony declares it.

`More → Engine…` (or a click on the engine in the status bar) shows the engine in use, its contracts, Node, and the installed versions. `Install engine` / `Update engine` downloads `agent-kit-engine-<version>.tar.gz` and `SHA256SUMS` of the newest kit release whose driver protocol is inside the range this Colony installs (`ENGINE_PROTOCOL_RANGE` in `src-tauri/src/engine.rs`, today `1.2.x`; read from each release's published `engine.json`, newest first), or of the version typed in, with the system `curl`, checks the sha256, unpacks it with `tar` into a temporary folder, checks `engine.json` against the range (an engine outside it is refused with what to do instead: update Colony, or pick another engine version), then moves it into place and makes it current. A newer kit release on a newer protocol is skipped, not installed blind. The engine it replaces stays installed for `Roll back`; older ones are removed. Signatures are not checked yet: no signing key exists, and the install says so. New agent runs use the new engine at once; Mission Control switches when the folder is reopened.

Node: the engine runs on a system `node` that satisfies its `node` range (`COLONY_NODE_BIN` or PATH), else on a Node build Colony installed. `Install Node runtime` downloads the pinned official Node build (24.22.0, Linux x64 and arm64 for now) from nodejs.org, checks it against `SHASUMS256.txt` and the sha256 pinned in engine.rs, and unpacks it into `<data dir>/colony/runtime/node-<version>/`.

## Host requests

An agent running inside Colony (an interactive `claude` / `codex` tab, a shell tab, or an `agent-kit run-plan` run started by Colony) that cannot or must not merge, rerun checks or push itself asks Colony instead; the same binary has a CLI mode for it:

```bash
"$COLONY_HOST_CLI" request merge-pr <number> [--method squash|merge|rebase] [--reason "..."] [--timeout 30m]
"$COLONY_HOST_CLI" request rerun-checks <run-id> | --pr <number>
"$COLONY_HOST_CLI" request push-branch [<branch>]
```

| | |
|---|---|
| Kinds | A closed allowlist: `merge-pr` (`gh pr merge N --squash` by default; never `--admin` or `--auto`), `rerun-checks` (`gh run rerun ID --failed`; with `--pr`, every failed run of that PR's head commit), `push-branch` (current branch by default, pinned when the request is filed; never forced). No shell, no arbitrary command. |
| Flow | The CLI writes a request into `COLONY_HOST_SPOOL` and waits (default 30 min; `--timeout` takes seconds or `90s` / `30m` / `2h`). The request becomes a card in the Git tab (badge on the tab, a line in the Inbox and the status bar). Colony runs the action with your own `git` / `gh` login only when you click Approve; Deny takes an optional reason that the agent receives. A forged response file in the spool only fools that requester: Colony never reads responses, it acts on the click. |
| Production | A merge into a production base needs a typed `yes` on the card. A `push-branch` of a production branch is refused (exit 64) before it reaches the spool: push it yourself from the Git tab. Production: `production`, `prod`, `release`, plus `main` / `master` when the repository has `origin/staging`. |
| Exit codes | `0` approved and succeeded, `2` denied (the reason is printed), `3` approved but the action failed (its output is printed), `4` timeout or Colony exited, `64` usage error, a refused request, or no Colony host (`COLONY_HOST_SPOOL` unset). |
| gh | Colony uses the `gh` on PATH (or `COLONY_GH_BIN`) and never reads, stores or relays a token. When `gh` is missing or logged out, the Pull requests card and the CI/CD tab say so. |

## Mission Control data

Colony runs the engine's unforked dashboard server for the opened folder (`node <engine>/dashboard/serve.mjs` with `MISSION_CONTROL_REPO_ROOT=<opened folder>` and `PORT=<free port>`, on loopback) and is a read-only client of its data API: `GET /dashboard-data.json` once, then `GET /api/events` (SSE, a full snapshot per change). The Colony page cannot read that server itself (the server answers CORS only for its own origin), so the Rust side fetches both over loopback HTTP/1.0 and forwards each snapshot unchanged (`src-tauri/src/mcdata.rs`); the stream reconnects on its own. The views read the snapshot contract of the kit (`docs/contracts/mission-control-snapshot.schema.json`, `dashboardDataVersion` 1.6.0), mostly its `missionControl` projection, and tolerate any nested field being absent. `GET /api/config` is asked too and is a 404 on kit 6.2.0 (the server only accepts config writes there), so the views use the snapshot's `system` summary. Colony never writes to the server. The status bar shows the feed (live or offline, age of the last snapshot, data version).

## Mission Control web panel

The kit's own page stays reachable under `More → Mission Control (web panel)`. Colony follows the kit's embeddable contract (`docs/mission-control-embedding.md` in the kit): it runs `node <engine>/dashboard/serve.mjs` with `MISSION_CONTROL_REPO_ROOT=<opened folder>` and `PORT=<free port>`, loads `http://127.0.0.1:<port>/?colony-skin=<skin>` in that tab, and defines `window.__MISSION_CONTROL_ACTIONS__` inside that frame only. The hook offers every record (always `kind: "copy"`, every string untrusted) to the Colony window first. The same frame script selects the panel's skin to match Colony's before the panel paints: it writes the kit's own preference key (`agent-kit:dashboard-skin`, `bare-metal` or `legacy`; `src/skin.ts` maps Colony's skin to the kit's value; kits before agent-kit #1260 spelled Bare Metal `cursor`, which newer kits still read as an alias). Colony runs a real host action for exactly two shapes and keeps the copy for everything else (`src/mcactions.ts`): a `filePicker` record holding a plain repo-relative path (no absolute, `~`, `..` or control characters; the Rust side still jails it to the folder) opens that file in a Colony tab, and a `chatInput` record that is exactly `/run-plan` or `/run-plan <plan basename>` starts an agent run (its own tab) of the folder's active plan after a native confirmation dialog. Terminal commands, PIDs, prompts, `/run-plan-all` and `/git-prod` stay copy, as does any record Colony does not answer within 1.5 s. The server is stopped when Colony exits (also on a crash, through a parent-death signal). Its log is under `~/.cache/colony/dashboard-<port>.log`.
