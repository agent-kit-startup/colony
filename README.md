# Mission Kit Colony

Colony is the Mission Kit desktop IDE: a Tauri 2 cockpit with Mission Control as its home screen. It drives the open [Agent Kit](https://github.com/agent-kit-startup/agent-kit) CLI and each vendor's own agent on the user's own subscription or API key.

Open source under the [Apache License 2.0](LICENSE) ([NOTICE](NOTICE)). Contributions come in under the Developer Certificate of Origin (`git commit -s`, see [CONTRIBUTING.md](CONTRIBUTING.md)). Colony collects no telemetry: its only network calls of its own are the engine and Node runtime downloads you start from `Run → Engine…` and the app update check you start from `Help → About Colony…` (see [PRIVACY.md](PRIVACY.md)).

## Status

Cockpit alpha. Omarchy 4 is the reference Linux platform: Linux features are designed and verified on Omarchy 4 first, other distributions and window managers keep working (see Omarchy below).

The cockpit is the center of the window. Its first tabs are Mission Control itself, as native views fed by the kit's own data (see Mission Control data): Mission, Plans, Queue, Inbox, Review, Git, CI/CD and Flight Log (Ctrl+1 to Ctrl+8). Every agent run opens as its own tab next to them, and so does an interactive agent. Files open in tabs after those.

| Area | What works |
|------|------------|
| Workspace | `Open folder` (Ctrl+O), the folder as the first CLI argument, recent folders on the welcome screen. File access is limited to the opened folder. |
| First run | Mission opens on a **First run** card when the folder has no Agent Kit, no readiness report, or open essential checks. It renders the kit's own report, `.cursor/context/readiness.json` (written by `agent-kit doctor`, which `/agent-kit-onboard` runs), in the order of `/agent-kit-onboard`'s first message: `Repository preparation: N of M essential checks ready.`, Detected, Fixed, and Next with exactly one action (the first essential check that is not `ready`, in report order). The essential checks are the mission list, with their status (`ready`, `auto_fix`, `needs_choice`, `manual`, `blocked`) as check chips. Without the kit the card is the whole view: install Agent Kit (`Install in a terminal` runs `npx @dadado/agent-kit-cli@latest install` in a terminal tab after a confirmation; its installer asks its own questions there), prepare the repository, start a first plan. Every other step opens your agent with `/agent-kit-onboard`; Colony keeps no checklist of its own and applies nothing itself, so CI/CD config, hooks, remotes and scaffold stay behind the kit's own questions. The report is read again on each Mission Control update, on window focus and with `Check again`. With an active plan the hero stays and the open checks shrink to one line above it; non-essential checks stay in the Inbox. |
| Mission | Home tab: the active plan from HANDOFF (lifecycle, progress, current and next to-do, gaps), `▶ Run plan`, `⏭ Run queue` (always enabled in an opened folder, like `agent-kit run-plan-all`: no active plan or stored queue needed, see Queue), `⌘ Open interactive`, the engine picker, then cards for what needs you (live gates answerable in place, attention items, gate-exit tickets), the agent runs, the saved chats (see Chats), the queue, the flight log, recent activity and the repository (branch flow, health checks). **Agent runs** lists every run Colony launched in this window: driver runs (the queue runner included, shown with its queue position and current plan), interactive vendor CLI tabs (plan actions such as `Run…` included) and queue runner terminal tabs, with plan, engine, state (starting, running, awaiting gate, ended with its exit code), start time and elapsed time; a click focuses its tab. Runs the kit snapshot reports (`run_plan` activity, agent processes of the folder) are merged in, without duplicating a Colony launch. The queue card lists the queue and links to the Queue view (Run queue itself is in the hero). It shows the queue as held when HANDOFF names another plan than the queue cursor while `Queue status` says running, or when a live queue run reports `held`. While a queue driver run is live, the hero shows its position, current plan, status and open gate; a click opens its tab. |

Empty views say what is missing and offer the next step (the kit's empty-state pattern); while the Mission Control server has not answered, `Retry` starts or reaches it again and `Show server log` follows its log in a terminal tab. |
| Commands | `View → Commands…` or Ctrl+Shift+P: the folder's slash commands from the kit, then Colony's own menu actions (every item of the menu bar and Workspace → Config, run as if picked from its menu), then Claude Code's built-in commands, with search. `Run` opens the interactive agent with `/<name>` as its first prompt, after a confirmation, only for the names in `PROMPT_SLASH` (`src-tauri/src/vendor.rs`): `run-plan`, `continue-plan`, `backlog-edit`, `archive-plan`, `backlog-cancel`, `backlog-delete` (the plan CRUD dropdown; each asks before it changes anything), `plan-review-triage`, `field-report-resolve`, `run-plan-all`, `handoff`, `summary`, and the first-run path `agent-kit-onboard`, `start-project`, `backlog-add`; the Inbox's `Ask agent` offers a subset of it (`ASKABLE` in `src/inbox.ts`, kept in parity by a test). Everything else is `Copy`. `/git-prod` is never run from Colony. |
| Queue | The `run-plan-all` queue from HANDOFF: order, cursor, outcomes, each plan's lifecycle and progress, the queue status note. `⏭ Run queue` starts the queue runner after a confirmation, with or without a queue in HANDOFF and with or without an active plan, as the kit's CLI does: with a stored queue it resumes it, without one it proposes a queue from the active plan and the backlog and asks you to confirm it (`queue-confirm`, answered like any other gate) before it writes HANDOFF; with no eligible plan it reports that and stops. On an engine with driver protocol 1.2.0 or newer (read from `engine.json`, or `engine-info --json` for `COLONY_AGENT_KIT_BIN` and the PATH fallback) it is a driver run, `agent-kit run-plan-all --events ndjson --backend <engine>`, in its own agent tab: its gates appear in the Inbox and are answered there, and the cursor and status follow its `queue_state` events (read-only, Colony never moves the cursor). On an older or unknown engine it opens in a terminal tab, where its numbered-list gates are answered. On driver protocol 1.3.0 or newer each driver run shows the tokens its engine reported (`tick_end` / `run_end` `usage`) in its agent tab, in the Agent runs card and in the Queue view's driver chat, against the folder's per-run token budget (driver chat settings; empty means none). Over the budget the run is marked in red and nothing else happens: the budget never stops a run or answers a gate. An older engine shows "no usage"; Colony does not count tokens from the agent's own stream. One gate can be pre-answered, and only if you turn it on per folder in the driver chat settings (off by default; kit ADR 2026-10-26, Amend 2026-10-28): `context-checkpoint` answered `Continue queue`, on driver protocol 1.4.0 or newer, while a token budget is set and the run's reported tokens (`hitl_gate.usage`) are within it. Colony sends it as `"source":"policy"`, so the kit records `policy pre-answer`, never an operator reply, and the transcript says "policy pre-answer". If any condition fails the gate waits for you as usual; every other gate is always yours. |
| Agent tab | One center tab per `agent-kit run-plan --events ndjson` run, opened and focused when the run starts (from `▶ Run plan`, a view, or `File → Run plan in another folder…`). A readable transcript: assistant text as prose, tool calls collapsible with their results, thinking folded, each tick's `LOOP_TICK_RESULT` as a summary card (exit, pending before and after, stop, usage limit, link to its Review), HITL gates inline with answer buttons and free text, answered gates marked. `Raw log`, `Stop at gate`, `Kill`. A collapsible **Context sources** strip under the head lists what that agent loads for its folder (see Open interactive). Several runs at once, one per folder (the kit has no run lock). Needs a folder with the kit installed and an active plan. |
| Open interactive | `⌘ Interactive` opens the engine's own CLI, unmodified (`claude` or `codex`; the Cursor engines open whichever of those is on PATH), in a center terminal tab in the opened folder, with the picker's model. Colony passes no credentials and reads none: the CLI uses your own login, and its environment is the same as a shell tab's. Agent tabs (driver runs, interactive and queue runner terminals) show a collapsible **Context sources** strip: what the agent loads for that folder, each with existence, line count and size, a click opens it in your editor. Claude: `~/.claude/CLAUDE.md`, `CLAUDE.md` (and `CLAUDE.local.md`) of the folder and of each parent up to your home folder, `AGENTS.md`, `.cursor/HANDOFF.md` and the auto-memory `~/.claude/projects/<folder with every non-alphanumeric character as ->/memory/MEMORY.md` with the count of memory files next to it (Claude Code keys that memory by the start folder, so a session started elsewhere loads another project's memory). Codex: `~/.codex/AGENTS.md`, `AGENTS.md` from the repository root down to the folder, HANDOFF. Cursor engines: `AGENTS.md`, `CLAUDE.md`, `.cursor/rules`, HANDOFF. Only paths, sizes and line counts are read (`src-tauri/src/context.rs`); a listed file outside the folder may then be opened like the settings file. |
| Chats | The **Chats** rail item lists the agent sessions saved for the opened folder, newest first: title, when it was last saved and the short session id. Claude Code saves every session per start folder (`~/.claude/projects/<folder with every non-alphanumeric character as ->/<session id>.jsonl`), so the list shows the sessions started in this workspace folder; subagent transcripts are not listed. The title is the name you gave the session, else Claude Code's own title, else the first prompt. A click (or `Resume`) opens `claude --resume <session id>` in a terminal tab in the folder, labelled with the title (the id is checked as a UUID before it reaches the command line; the session keeps its own model); a chat already open in a resume tab is focused instead. `↻ Refresh` reads the list again; it is also read when a folder opens and when an interactive claude tab ends. Up to 200 sessions are listed, with the total. Only the titles are read, line by line, and cached by file size and time (`src-tauri/src/chats.rs`). Codex and Cursor sessions are not listed yet. Terminal tabs themselves are not restored after a restart. |
| Inbox | Live gates: every open HITL gate from every run in this window, any engine, oldest first (tab badge = their count). A button or free text answers it: the driver-protocol line `{"type":"hitl_reply","askId":...,"reply":...}` goes to that run's stdin only. A card leaves when it is answered, the tick ends or the run exits. Colony never answers a gate by itself. Below: Mission Control's attention items (open the file, or `Ask agent` for an allowlisted kit command such as `/plan-review-triage`; anything else copies) and pending gate-exit tickets. |
| Review | Every tick of every run in this window with the files it changed (added, modified, deleted, renamed; new untracked files included, `.gitignore` respected), a Monaco side-by-side diff per file, commits made during the tick, the `LOOP_TICK_RESULT` line, "Copy patch". A tick is the working tree change from the previous tick end (or the run start) to its own end, captured as git tree objects through a throwaway index, so your index, worktree and refs are never touched; an edit you make between two ticks shows up in the next tick. A run killed mid-tick still gets its partial tick. |
| Git | Branch flow from the snapshot (upstream, vs staging, vs main, staging vs main), last commit and graph; working tree status, per-file diff, commit (optionally `git add -A`; hooks always run), push without force. Pushing a production branch needs a typed `yes`: `production`, `prod` and `release` always, and `main` / `master` only when the repository also has `origin/staging` (without `staging`, `main` is the development branch and pushes or merges into it are a plain click). Production promotion: Colony never runs `/git-prod` or any prod promotion; after a typed `yes` it copies `/git-prod` for your own agent session. Above them: **Requests**, one approval card per host request (see Host requests) with the request nonce, kind, arguments, reason, folder and the PR context (title, base ← head, mergeable state, checks, `View diff`, `Open PR`); the tab badge counts them. **Pull requests**: the open PRs with their checks summary and a `Merge…` button that opens the same card under the same production rule. |
| CI/CD | Recent workflow runs (`gh run list`) of the current branch, of the open pull request branches, or all, with `Rerun failed` (`gh run rerun <id> --failed`) on a failed run. |

| Explorer | Lazy file tree (`.git` hidden), refresh button, its own splitter; View → Show or hide the Explorer. A click selects a row (1px border). `File → New file` and `File → New folder` create in the selected folder (a selected file: its folder; nothing selected: the root), with the name typed inline in the tree; a new file opens in the editor. Right-click a row, or the empty Explorer, for Colony's menu: New file, New folder, Rename (typed in place), Delete (moves it to the system trash after a question; Colony never deletes for good), Copy path, Open terminal here (a drawer shell in that folder), Open in editor. Every operation is a Rust command jailed to the folder: no `..`, nothing outside it, never over an existing name; a symlink is renamed or trashed itself, and one pointing outside the folder is refused. |
| Editor | Monaco with one tab per file, dirty marker, `File → Save` (also in the Commands palette, and Ctrl+S) with a `Saved` or `Save failed` notice in the status bar on every outcome (a view or a terminal tab active: `Nothing to save`), `File → Save as…` (a workspace-relative name typed in Colony; the file is created inside the folder and never overwrites one, the original tab keeps its text), Ctrl+W close (asks before dropping unsaved changes), Ctrl+P quick open. The native menu shows no shortcuts (GTK would take the keys from the terminals and the editor); the palette rows show them. A Preview \| Editor switch heads every Markdown tab; Explorer opens Markdown in the editor. In the preview a repo link opens that file in Colony and a web link copies its address. |

## Install (Linux x86_64)

```bash
curl -fsSL https://github.com/agent-kit-startup/colony/releases/latest/download/install.sh | sh
```

`packaging/install.sh` checks the release signature (minisign key `9A9BB4349C2248C6`, with `minisign` or OpenSSL 3) and the sha256 before it installs anything, installs per user without sudo, and `--uninstall` removes it again. `Help → About Colony…` shows the version and the distribution channel: the AppImage of a release updates itself in place (signed, user-started); a tarball install updates by running the install line again; distro packages update through the package manager. Releases come from a pushed `v<version>` tag (`.github/workflows/release.yml`) and live in this repository's GitHub Releases; `install.sh` installs the Latest one unless `--version` names another. `https://colony.missionkit.io/install.sh` is meant to redirect to the URL above (not set up yet). See [docs/release.md](docs/release.md) for the release files, the identity checklist and the install smoke.

## Requirements (Linux)

- Rust stable via rustup (`~/.cargo/bin` on PATH for builds).
- Node.js 20+ and pnpm 10.
- Tauri 2 system libraries: `webkit2gtk-4.1`, `gtk3`, `libsoup3`, `base-devel` (Arch package names).
- An Agent Kit engine: `Run → Engine… → Install engine` (see Engine), or `COLONY_ENGINE=<kit checkout>` for development. An `agent-kit` on PATH (`npm i -g @dadado/agent-kit-cli`) still works as a fallback, flagged as an unmanaged engine.

## Build and run

```bash
pnpm install --frozen-lockfile
pnpm tauri dev                   # development, hot reload on http://localhost:1420
pnpm tauri build                 # release binary + .deb bundle
./src-tauri/target/release/colony ~/code/some-repo
```

`pnpm tauri build` writes `src-tauri/target/release/colony` and `src-tauri/target/release/bundle/deb/Colony_<version>_amd64.deb`. A plain `cargo build --release` is not enough for a runnable binary: the Tauri CLI enables the custom protocol that serves the built frontend.

## Launcher (per user, no sudo)

```bash
pnpm tauri build
packaging/install-local-launcher.sh
```

This writes `~/.local/bin/colony` (wrapper around `src-tauri/target/release/colony`) and `~/.local/share/applications/colony.desktop`, so Colony shows up in the app launcher. `colony ~/code/some-repo` opens a folder directly. Rebuilding updates the same binary; the launcher does not need to be reinstalled.

## Omarchy

Omarchy 4.x is the reference Linux platform: a Linux feature is designed and verified there first. The surfaces below act only where Omarchy is installed; without Omarchy Colony behaves exactly as on any other Linux desktop. It reads Omarchy state freely and never writes under `~/.config/hypr`, `~/.config/omarchy` or `~/.local/state/omarchy` without an explicit step of yours, which lists the files first and has a matching remove step.

| Surface | What Colony does |
|---------|------------------|
| Default agent | When Colony has no engine choice for the folder yet, the engine picker starts on the agent in `~/.config/omarchy/defaults/agent` (`omarchy-default-agent`): `claude`, `codex` and `cursor-agent` map one to one, and the note under the picker says "Omarchy default agent". The other Omarchy agents (`opencode`, `pi`, `gemini`, ...) have no Agent Kit backend, so Colony keeps its own default (`claude`). A choice you make in the picker always wins. The file is only read. |
| Theme and font | `Workspace → Config → Skin → Omarchy (system theme)`, the default on Omarchy while `ui.skin` is unset (a skin you pick wins). Colony reads `~/.local/state/omarchy/current/theme/colors.toml`, the palette `omarchy-theme-set` writes, and maps it onto the same nine surface tokens and the semantic colours (`src-tauri/src/omarchy.rs`, with the roles of Omarchy's own `t3code.json.tpl`: canvas and terminal on `background`, panels on `dark_background`, focus on `accent`; card and text steps are mixed from background and foreground, with muted text kept at 4.5:1 contrast or better on all 22 themes Omarchy 4.0.6 ships). Light themes (`mode = "light"`) switch the window, Monaco and the terminals to light. The monospace font is the one `omarchy-font-current` reports (`fc-match monospace`), first in the editor and terminal stacks. A theme or font switch applies within about two seconds, without a restart: Colony polls `colors.toml`, `theme.name` and `~/.config/fontconfig/fonts.conf` (theme-set replaces the theme directory, so a directory watch would not survive it). Read-only: no themed template, no `theme-set.d` hook. Not yet: the font size stays 13 px (Omarchy has no font size setting to follow). |
| Single instance | One window per Colony binary and engine (`COLONY_ENGINE`). `colony`, `colony <folder>`, the desktop entry and `omarchy-launch-or-focus` reach the running window over a Unix socket in `$XDG_RUNTIME_DIR` (`src-tauri/src/instance.rs`): it raises itself (on Hyprland it also asks the compositor to focus it with `hyprctl dispatch`, switching to its workspace, as `omarchy-launch-or-focus` does; `src-tauri/src/hyprland.rs`) and, for another folder, opens that folder the way `Open folder` does (unsaved files are asked about first; cancel and the window keeps its folder). A path that is not a directory, `--new-instance`, `COLONY_SMOKE` or no `$XDG_RUNTIME_DIR` start a window of their own; any socket error does too (fail open). This works on any Linux desktop, not only Omarchy. |
| Window | Window class and app id `colony` (`StartupWMClass=colony`), so `omarchy-launch-or-focus colony` matches it. Native decorations, which Hyprland negotiates away: no client-side titlebar or window buttons under a tiling WM. |
| Keybinding | `packaging/install.sh --omarchy-snippet` prints an optional Omarchy 4 Lua snippet, `o.bind("SUPER + SHIFT + I", "Colony", { launch = "colony", focus = "^colony$" })` (free in the 4.0.6 defaults) plus a commented `o.window` example, and exits. It writes nothing: you paste it into `~/.config/hypr/bindings.lua` yourself, and delete it to remove it. |
| Notifications | A new gate raises a standard freedesktop notification (`tauri-plugin-notification`, app name `colony`, not `notify-send`, so omarchy-shell keeps it). Clicking it in omarchy-shell invokes the notification's `default` action, which the plugin registers because Colony listens for actions; Colony then focuses its window and opens the Inbox on that gate. If the window is gone, omarchy-shell falls back to focusing the app by its class, `colony`. Checked against the plugin 2.7.0 and omarchy-shell 4.0.6 sources; the live click is part of the Omarchy dogfood. |
| Bar widget and menu | `Workspace → Config → Omarchy integration…` (Omarchy only) lists every file and command first and runs nothing until you press Install; Remove undoes only what Colony wrote. The bar widget is an omarchy-shell plugin, `~/.config/omarchy/plugins/missionkit.colony/` (`packaging/omarchy/missionkit.colony/`, passes `omarchy plugin validate`), enabled with `omarchy-shell shell rescanPlugins` and `omarchy-plugin-enable`, so Omarchy's own tooling places it in `shell.json`: the Colony mark in the bar's colours (its urgent colour while a gate waits) with the open gate count, a tooltip with the live runs of every Colony window, a left click opens the Inbox when a gate waits (else focuses Colony), a right click focuses Colony. It is installed by hand, not through `omarchy plugin add`, so `omarchy plugin update` does not manage it: Update in the same panel rewrites it. The menu entries (Colony → Open Colony, Colony Inbox, Open folder in Colony, each hidden when `colony` is not on PATH; the menu takes a font glyph only, so Colony shows as a ringed planet there) go into `~/.config/omarchy/extensions/omarchy-menu.jsonc` between `// colony:begin` and `// colony:end`; a `colony` entry of your own there blocks them. Both need `colony` on PATH (the installer, the launcher and packages put it there). |
| `colony status` | `colony status --bar` prints the open gates and live runs of the running Colony windows as Waybar-style JSON (`text`, `tooltip`, `class`, `gates`, `runs`, `windows`) and exits; the bar widget polls it every 3 s. Each window on Omarchy keeps its own `$XDG_RUNTIME_DIR/colony/<pid>/status.json`, removed on exit. It also works as a `"type": "command"` bar module if you would rather not install the plugin. |
| `colony --inbox`, `--open-folder` | Ask the running window to open its Inbox or the folder picker (and raise itself); on a first launch, the view opens once the folder has. |

## Settings

`~/.config/io.missionkit.colony/settings.json` (the ⚙ button creates it and opens it in a Colony tab). Read on every use: a saved edit applies at once. Colony changes only the keys it writes, one write at a time (also across Colony processes, via `settings.json.lock`), so a layout save and a skin change never drop each other or an edit you saved meanwhile.

```json
{
  "ui": { "skin": "bare-metal", "titleBar": "native" },
  "editor": { "command": ["zed", "{path}"], "terminal": false },
  "workspaces": { "/home/me/code/repo": { "backend": "claude" } }
}
```

`ui.skin` is the look of the whole window: `bare-metal` (the default, neutral greys), `legacy` (the slate palette of the kit's original Mission Control) or `omarchy` (the live Omarchy theme, offered and used by default only on Omarchy; see Omarchy); `Workspace → Config → Skin` switches and saves it. Both are one design token set, `src/tokens.css`, generated from the kit's skin token contract (`src/contracts/mission-control-skins.json`, a verbatim copy of the kit's `docs/contracts/mission-control-skins.json`) by `pnpm tokens`; `pnpm build` fails when the two differ. The names are the web Mission Control's own (`--bg-primary`, `--border`, `--text-muted`, `--green-bg`, `--mc-radius-chrome`, `--mc-space-lg`, ...) and Colony has no second color name set, so a skin is the same nine surface colors in both. The chrome, the native views, Monaco and the terminals read it. The native views also reuse the kit web page's components: card headers with an icon and a title-case label, status pills, per-to-do segmented progress, the previous / current / next steps, monospace metadata rows and action chips (`src/ui.ts`, icons in `src/icons.ts`).

`ui.titleBar` is `native` (the default; also what an unknown value gives) or `custom`, read when the window opens, so `Workspace → Config → Title bar` saves it for the next start. Under a tiling window manager Colony always opens native and ignores `custom` (the file may be shared with a non-tiling desktop, where it applies). `ui.layout` is written by Colony on every panel change: `terminalDock` (`bottom`, `top`, `side`), `terminalVisible`, `explorerVisible`, `railPosition` (`left`, `right`), `railLabels` (`false` for icons only), and the splitter sizes in CSS pixels, `explorerWidth`, `terminalHeight` (docked at the bottom or the top) and `terminalWidth` (at the side); an unset field keeps the default, and `settings_set_layout` refuses a value outside those (nothing is written then).

Open in my editor picks, in order: `editor.command` (a string split on spaces, or an argv array; the path is appended or replaces `{path}`), `$VISUAL`, `$EDITOR`, then `xdg-open`. `$VISUAL` / `$EDITOR` run in a new Colony terminal tab through `sh -c '<editor> "$@"'`, the way git runs them, so terminal editors (and wrappers such as `omarchy-launch-editor --inline`) work; a configured command runs detached unless it is a terminal editor (`nvim`, `vim`, `hx`, ...). `editor.terminal` forces either way. The path is always its own argument.

## Engine

Colony runs the open Agent Kit as a managed engine (the kit's ADR `2026-10-19_colony-managed-engine-distribution`): it installs, updates and rolls back the kit itself, and never needs npm. `src-tauri/src/engine.rs` resolves it in this order:

1. `COLONY_ENGINE=<path>`: a kit checkout or an extracted engine, for developing the engine and Colony against the same working tree. A checkout without `engine.json` is asked with `agent-kit engine-info --json`.
2. The managed engine in `<data dir>/colony/engine/<version>/` (Linux: `~/.local/share/colony/engine/`): the current one of `state.json`, else the highest installed version Colony supports.
3. `agent-kit` on PATH, as before; the status bar says `⚠ unmanaged engine`.

`COLONY_AGENT_KIT_BIN` and `COLONY_DASHBOARD_SERVE` still win for agent runs and for Mission Control (the smoke fixtures use them).

Supported range: driver events protocol 1.x and Mission Control data 1.x (`DRIVER_PROTOCOL_MAJOR`, `DASHBOARD_DATA_MAJOR` in engine.rs), read from the engine's `engine.json`. A kit release inside the range installs without a Colony release; a new major is refused until Colony declares it.

`Run → Engine…` (or a click on the engine in the status bar) shows the engine in use, its contracts, Node, and the installed versions. `Install engine` / `Update engine` downloads `agent-kit-engine-<version>.tar.gz` and `SHA256SUMS` of the newest kit release whose driver protocol is inside the range this Colony installs (`ENGINE_PROTOCOL_RANGE` in `src-tauri/src/engine.rs`, today `1.2.x-1.5.x`; read from each release's published `engine.json`, newest first), or of the version typed in, with the system `curl`, checks the sha256, unpacks it with `tar` into a temporary folder, checks `engine.json` against the range (an engine outside it is refused with what to do instead: update Colony, or pick another engine version), then moves it into place and makes it current. A newer kit release on a newer protocol is skipped, not installed blind. The engine it replaces stays installed for `Roll back`; older ones are removed. Signatures: once the kit's engine signing key exists and its public key is set in `ENGINE_SIGNING_PUBKEY` (`src-tauri/src/engine.rs`), every install also downloads `SHA256SUMS.minisig` and checks it (minisign, Ed25519) over `SHA256SUMS` before the sha256 is trusted, and refuses a release without a valid one. Until then no key exists, only the sha256 is checked, and the install says so. New agent runs use the new engine at once; Mission Control switches when the folder is reopened.

Node: the engine runs on a system `node` that satisfies its `node` range (`COLONY_NODE_BIN` or PATH), else on a Node build Colony installed. `Install Node runtime` downloads the pinned official Node build (24.22.0, Linux x64 and arm64 for now) from nodejs.org, checks it against `SHASUMS256.txt` and the sha256 pinned in engine.rs, and unpacks it into `<data dir>/colony/runtime/node-<version>/`.

## Host requests

An agent running inside Colony (an interactive `claude` / `codex` tab, a shell tab, or an `agent-kit run-plan` run started by Colony) that cannot or must not merge, rerun checks or push itself asks Colony instead; the same binary has a CLI mode for it:

```bash
"$COLONY_HOST_CLI" request merge-pr <number> [--method squash|merge|rebase] [--reason "..."] [--timeout 30m]
"$COLONY_HOST_CLI" request rerun-checks <run-id> | --pr <number>
"$COLONY_HOST_CLI" request push-branch [<branch>]
"$COLONY_HOST_CLI" request open-pr promote | staging-sync
```

| | |
|---|---|
| Kinds | A closed allowlist: `merge-pr` (`gh pr merge N --squash` by default; never `--admin` or `--auto`), `rerun-checks` (`gh run rerun ID --failed`; with `--pr`, every failed run of that PR's head commit), `push-branch` (current branch by default, pinned when the request is filed; never forced), `open-pr` (one of two fixed ship-lane PRs: `promote` opens `staging` → `main`; `staging-sync` pushes `origin/main`'s tip, never forced, to a new `chore/sync-staging-main-<sha7>` branch and opens its PR into `staging`; Colony picks the branches from the local `origin/*` refs and writes the title and body, and refuses when there is nothing to promote or sync). No shell, no arbitrary command. |
| Flow | The CLI writes a request into `COLONY_HOST_SPOOL` and waits (default 30 min; `--timeout` takes seconds or `90s` / `30m` / `2h`). The request becomes a card in the Git tab (badge on the tab, a line in the Inbox and the status bar). Colony runs the action with your own `git` / `gh` login only when you click Approve; Deny takes an optional reason that the agent receives. A forged response file in the spool only fools that requester: Colony never reads responses, it acts on the click. |
| Production | A merge into a production base needs a typed `yes` on the card. A `push-branch` of a production branch is refused (exit 64) before it reaches the spool: push it yourself from the Git tab. Production for a host request: `production`, `prod`, `release`, `main` and `master`, always (the request's folder belongs to the requester, so its local refs do not decide). The Git tab's own push button counts `main` / `master` only when the repository has `origin/staging`. A PR from another repository (a fork) never merges into a production base from Colony, whatever is typed. Approve acts on what the card showed: a merge runs with `--match-head-commit <head on the card>` and is refused if the base changed; an `open-pr` whose refs moved is refused. |
| Exit codes | `0` approved and succeeded, `2` denied (the reason is printed), `3` approved but the action failed (its output is printed), `4` timeout or Colony exited, `64` usage error, a refused request, or no Colony host (`COLONY_HOST_SPOOL` unset). |
| Git e CI/CD | The Git tab is one bento grid like the kit web page's Git e CI/CD section: the Ship lane tile leads (the snapshot's `shipLane`, Mission Control data 1.8.0, Agent Kit 6.9.0 or later; an older engine shows "Update the engine" and no actions), then Requests, Pull requests, the branch flow, the working tree and Production promotion. A Ship lane row offers a button only for an allowlisted kind: merge the release-close PR into staging (`merge-pr`, squash), open the staging → main PR (`open-pr promote`), merge it (`merge-pr`, merge commit, typed `yes`), rerun the failed jobs of the tag's CI run (`rerun-checks`), open the staging sync PR (`open-pr staging-sync`). Each button opens a card; nothing runs before Approve. `/git-prod`, `/kit-prod`, a tag push or a push to `main` are never a button: the rows copy the command. |
| gh | Colony uses the `gh` on PATH (or `COLONY_GH_BIN`) and never reads, stores or relays a token. When `gh` is missing or logged out, the Pull requests card and the CI/CD tab say so. |

## Mission Control data

Colony runs the engine's unforked dashboard server for the opened folder (`node <engine>/dashboard/serve.mjs` with `MISSION_CONTROL_REPO_ROOT=<opened folder>` and `PORT=<free port>`, on loopback) and is a read-only client of its data API: `GET /dashboard-data.json` once, then `GET /api/events` (SSE, a full snapshot per change). The Colony page cannot read that server itself (the server answers CORS only for its own origin), so the Rust side fetches both over loopback HTTP/1.0 and forwards each snapshot unchanged (`src-tauri/src/mcdata.rs`); the stream reconnects on its own. The views read the snapshot contract of the kit (`docs/contracts/mission-control-snapshot.schema.json`, `dashboardDataVersion` 1.6.0), mostly its `missionControl` projection, and tolerate any nested field being absent. `GET /api/config` is asked too and is a 404 on kit 6.2.0 (the server only accepts config writes there), so the views use the snapshot's `system` summary. Colony never writes to the server. The status bar shows the feed (live or offline, age of the last snapshot, data version).

## No web panel

Colony no longer embeds the kit's web page (plan colony-sidebar-native-kit, to-do s3; kit ADR `2026-10-08_mission-control-embeddable-contract.md` amend 2026-10-28): there is no Mission Control tab, View menu row, frame hook (`window.__MISSION_CONTROL_ACTIONS__`) or host-action seam, and the CSP says `frame-src 'none'`. The kit's page stays a standalone surface (`agent-kit dashboard` in a browser). Colony still runs the engine's dashboard server for the opened folder, only as the data API above, and stops it when Colony exits (also on a crash, through a parent-death signal); its log is under `~/.cache/colony/dashboard-<port>.log`.
